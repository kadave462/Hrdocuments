Product Vision

E jabo is a Software-as-a-Service HR platform built for medium-to-large organizations. Each company (tenant) operates in complete isolation — their employees, payroll, settings, and permissions are fully separate from every other company. A single person can hold positions at multiple companies simultaneously, switching contexts via a single login.

Key Differentiator
Multi-tenancy with cross-company user identity: one national ID = one person, but they can hold jobs at multiple companies with different roles at each.

What is a DTO?
A DTO (Data Transfer Object) is a plain Java class used to carry data between layers or services. It is never persisted — it only defines the shape of a request body or a response payload. Services never share database entities directly; they always exchange DTOs over HTTP.

Key Implementation Patterns
Multi-Tenancy via companyId Headers ▶

The API Gateway's AuthorizationFilter extracts the JWT and injects these headers on every forwarded request:

userId, companyId, employeeId, credentialsId, username

Backend services never parse JWTs themselves — they just read these headers. This ensures every database query can be scoped to the correct company automatically.

Axios Extended Instance Pattern ▶

Frontend uses a factory function createExtendedInstance('/api/v1/auth') to create per-service Axios instances that inherit the base URL, JWT interceptor, and 401 redirect logic. BASE_URL is read from NEXT_PUBLIC_DEV_BASE_URL environment variable.

Bulk Import with Hibernate Batching ▶

When importing thousands of employees from CSV/Excel, Employee Service uses Hibernate batch inserts (spring.jpa.properties.hibernate.jdbc.batch_size) combined with HikariCP connection pool tuning to handle bulk DB writes efficiently without creating individual connections per employee.

Async Email with @Async ▶

The EmailService.sendWelcomeEmail() method is annotated with @Async so HTTP responses return immediately while emails are sent in background threads. The class also carries @EnableAsync. This prevents bulk-import API calls from timing out waiting for 1000+ welcome emails to send.

Database-per-Service Pattern ▶

Each microservice has its own PostgreSQL database: auth_db, company_db, employee_db, file_db. Services cannot directly query each other's databases — they must call the owning service's REST API. This enforces service boundaries and allows independent schema evolution.

OTP Authentication Flow ▶

No password on the login screen. Step 1: POST /generate-otp → saves 6-digit OTP in user_otp table with 10-min expiry, sends email. Step 2: POST /verify-otp → validates OTP, issues JWT. Token contains userId, companyId, employeeId. Debug tip: OTP is printed to auth-service logs before the email call.

Option A — Run Everything with Docker Compose (Recommended)
What Docker Compose starts
Eureka Server → Auth Service → Company Service → Employee Service → File Service → API Gateway. All connected on the hr-network bridge network. Health checks ensure Eureka is healthy before others start.
Step 1 — Update DB connection in docker-compose.yml ▶

The docker-compose.yml currently points to the remote production DB (142.93.28.84:5432). For local testing, either keep this (uses prod data) or run your own PostgreSQL and update the env vars:

SPRING_DATASOURCE_URL: jdbc:postgresql://localhost:5432/auth-service
SPRING_DATASOURCE_USERNAME: postgres
SPRING_DATASOURCE_PASSWORD: postgres

Repeat for company-service, employee-service, file-service — change the DB name each time (company-service, employee-service, file-service).

Step 2 — Build & start all backend services ▶

Run from the project root (where docker-compose.yml lives):

# Build all Docker images from source
docker compose build

# Start all services in detached mode
docker compose up -d

# Watch startup logs
docker compose logs -f
Wait ~60–90 seconds
Eureka has a 90-second startup period. Check http://localhost:8761 — all 5 services should appear as UP before testing.
Step 3 — Start the frontend separately ▶

The frontend is not in docker-compose.yml — run it manually:

cd hr-fe-service

# Create the .env file
copy .env.example .env

# Install dependencies
pnpm install

# Start dev server on port 3003
pnpm dev

Open http://localhost:3003 in your browser. The frontend calls the gateway at http://localhost:8090 via NEXT_PUBLIC_DEV_BASE_URL.

Option B — Run Services Manually (Without Docker)
When to use this
Use manual mode when you want to edit and hot-reload a specific service without rebuilding Docker images. Run the services you're working on manually; use Docker for the rest.
Step 1 — Create the 4 PostgreSQL databases ▶

Each service has its own database. Run this in psql or pgAdmin:

CREATE DATABASE auth_db;
CREATE DATABASE company_db;
CREATE DATABASE employee_db;
CREATE DATABASE file_db;

Tables are auto-created by Hibernate on first run (spring.jpa.hibernate.ddl-auto=update). You do not need to run SQL scripts manually.

Step 2 — Start Eureka Server (start this first, always) ▶
cd hr-be-services/eureka-server
./mvnw spring-boot:run

Wait until you see Tomcat started on port 8761. Then open http://localhost:8761 — you'll see the Eureka dashboard.

Step 3 — Start backend microservices (each in a new terminal) ▶

Open 4 more terminals and run one service per terminal in this order:

# Terminal 2 — Auth Service (port 8081)
cd hr-be-services/auth-service && ./mvnw spring-boot:run

# Terminal 3 — Company Service (port 8082)
cd hr-be-services/company-service && ./mvnw spring-boot:run

# Terminal 4 — Employee Service (port 8083)
cd hr-be-services/employee-service && ./mvnw spring-boot:run

# Terminal 5 — File Service (port 8084)
cd hr-be-services/file-service && ./mvnw spring-boot:run

# Terminal 6 — API Gateway (port 8090) — start last
cd hr-be-services/api-gateway && ./mvnw spring-boot:run
Check Eureka before testing
Visit http://localhost:8761. All services should appear as UP. If a service shows DOWN, check its terminal for startup errors (usually a DB connection issue).
Step 4 — Start the Frontend ▶
cd hr-fe-service
copy .env.example .env
pnpm install
pnpm dev

Frontend runs at http://localhost:3003. It needs the gateway (:8090) to be running to make API calls. Make sure .env has NEXT_PUBLIC_DEV_BASE_URL=http://localhost:8090.

First-Time Data Setup (Empty DB)
Local DB is empty on first run
The local PostgreSQL databases start empty. Production accounts don't exist locally. You must register a company and user before anything else works.
1. Open Swagger: http://localhost:8090/swagger-ui.html
2. Find the company-controller section → POST /api/v1/company → fill in company name, admin email, password → Execute
3. Check docker-compose logs auth-service (or the auth-service terminal) for the email verification link — click it to verify the email
4. Now you can log in via POST /api/v1/auth/generate-otp (see Login Flow below)
Login Flow — Postman Step by Step
Step 1 — Generate OTP ▶
MethodPOST
URLhttp://localhost:8090/api/v1/auth/generate-otp?isResend=false
Body (JSON){ "email": "youruser@example.com", "password": "Password@123" }

SendGrid is broken locally — use logs instead
The email will fail with 401 locally (SendGrid key issue). The OTP is still printed to the auth-service console/logs. Find it with:
docker-compose logs auth-service | findstr "OTP"
or scroll the auth-service terminal and look for "OTP:" in the output.
Step 2 — Verify OTP and get JWT token ▶
MethodPOST
URLhttp://localhost:8090/api/v1/auth/verify-otp
Body (JSON){ "email": "youruser@example.com", "otp": "123456" }
ResponseReturns a JWT token string — copy this, you need it for all other requests

JWT expires after 24 hours (86400000ms). Repeat Steps 1–2 to get a fresh token.

Step 3 — Use the JWT on all protected endpoints ▶

Every request to a protected endpoint must include the JWT in the Authorization header:

Authorization: Bearer <paste-your-jwt-here>

In Postman: Go to the request → Authorization tab → Type: Bearer Token → paste the JWT in the Token field.

In Swagger UI: Click the "Authorize" button at the top right → paste Bearer <your-token> → Authorize.

Known Issues & Workarounds
SendGrid 401 — OTP emails don't arrive locally
The SendGrid API key in the local config is expired or rate-limited. The OTP is still printed to auth-service logs before the SendGrid call fails — check Docker logs or the terminal and look for "OTP:" in the output.
Empty database on first run
Local PostgreSQL starts empty — no users, no companies. Run POST /api/v1/company in Swagger to register a company and admin user before testing anything else.
Frontend .env must point to localhost:8090
The .env.example file points to http://142.93.28.84:8870 (production). Copy it to .env and change NEXT_PUBLIC_DEV_BASE_URL to http://localhost:8090 for local development.
Eureka must start first — always
If other services start before Eureka is fully up, they fail to register and the gateway can't route to them. The Docker Compose health checks (90s startup period, 10 retries) handle this automatically. For manual startup, wait until you see Eureka at http://localhost:8761 before starting other services.
Employee Service uses Redis for caching
Employee Service has a two-level cache (EhCache + Redis). If Redis is not running locally, the service will still work but may log cache errors. Install Redis or use Docker (docker run -d -p 6379:6379 redis) if you want caching to work correctly.
Frontend port is 3003 in dev, 3000 in Docker
pnpm dev starts on port 3003. The Dockerfile and Docker Compose expose port 3000. Don't confuse the two — if you run Docker, open http://localhost:3000; if you run pnpm dev, open http://localhost:3003.

Technical Debt & Planned Improvements
Migrate email from SendGrid to Notification Service
Auth-service currently sends emails directly via SendGrid (single point of failure, expired key in local dev). The Notification Service uses SMTP (more reliable) and also supports SMS. Auth-service should call Notification Service at POST /api/v1/notifications/email/otp instead.
Add Notification Service to Docker Compose
The notification-service exists in the codebase but is not currently in the docker-compose.yml. It needs to be added with its SMTP credentials and IVAS SMS API key.
Add seed data for local development
No seed data exists in the project. Every fresh Docker Compose startup requires manual registration of a company and user. A seed SQL script or Spring Boot data.sql file would eliminate this friction.
Centralized logging (ELK stack)
Currently logs are per-container via Docker. A centralized log aggregation solution (Elasticsearch, Logstash, Kibana) or Loki + Grafana would enable cross-service request tracing and alerting.
Automated integration tests
Current testing is manual via Postman and Swagger. Adding Testcontainers-based integration tests to the Maven build would catch regressions before deployment and verify inter-service contracts.
API versioning strategy
All endpoints use /api/v1/ prefix. As the product evolves, a clear versioning policy (deprecation headers, v2 routes) will be needed to avoid breaking existing integrations.

Two-step login — no persistent password on the login screen
Step 1 is OTP generation (requires email + password to authenticate first). Step 2 is OTP verification which issues the JWT. This is passwordless from the user's perspective after first login.
STEP 1 — Generate OTP (POST /auth/generate-otp)
1
User opens login page — enters their email address and password. Clicks "Send OTP". Frontend calls POST /api/v1/auth/generate-otp?isResend=false with body { "email": "...", "password": "..." }.
2
API Gateway receives the request — checks the path against its public route list (no JWT validation on this endpoint). Routes to lb://auth-service via Eureka load balancing.
3
AuthService.generateOtp() — calls Spring Security's AuthenticationManager.authenticate() with a UsernamePasswordAuthenticationToken(email, password). This triggers the full authentication chain.
4
CustomUserDetailsService.loadUserByUsername(email) — queries credentials table by email. If not found, throws UsernameNotFoundException. Returns Credentials entity as UserDetails.
5
BCrypt password comparison — Spring Security compares the submitted password against the BCrypt hash stored in credentials.password. If wrong, throws BadCredentialsException → auth-service returns 400 "Invalid credentials".
6
Authentication succeeds — if isResend=true, checks the last OTP in user_otp table. If it was sent less than 60 seconds ago, throws 400 "Please wait 60 seconds". Otherwise proceeds.
7
OtpUtil.generateOtp() — generates a 6-digit random numeric string. A UserOtp entity is built: email, otp, createdAt=now(), expiresAt=now()+10min, isVerified=false. Saved to user_otp table.
8
Debug tip — System.out.println(otp) is called BEFORE the email. So even if SendGrid fails, the OTP appears in Docker logs: docker-compose logs -f auth-service
9
EmailService.sendOtpEmail(email, otp) — calls SendGrid API with a Thymeleaf-rendered HTML email containing the 6-digit OTP. This may throw silently if the SendGrid key is expired (local dev issue).
10
Response returned — "OTP sent successfully". The OTP is valid for 10 minutes. User checks their email (or Docker logs in dev).
STEP 2 — Verify OTP & Issue JWT (POST /auth/verify-otp)
11
User enters OTP — frontend calls POST /api/v1/auth/verify-otp with body { "email": "...", "otp": "123456" }. Public endpoint, no auth header.
12
AuthService.verifyOtp(email, otp) — queries user_otp table: findByEmailAndOtpAndIsVerifiedFalse(). If no matching record found → returns false → 400 "Invalid OTP".
13
Expiry check — userOtp.getExpiresAt().isBefore(LocalDateTime.now()). If true (OTP expired) → returns false → 400. If valid → sets isVerified=true and saves.
14
verifyOtp returns true → controller calls authService.generateToken(email) to build the JWT.
15
Role check — credentials loaded from DB. If role == ROLE_SUPER_ADMIN: skips Employee Service call, uses ADMIN + COMMON permissions only. Otherwise proceeds to step 16.
16
Employee Service call (regular users) — auth-service calls GET lb://employee-service/employee-roles/{userId}/{companyId} using a pre-auth header JWT. Response: GetCompanyUserRolesDto { companyId, employeeId, userRoles: Set<UUID> }.
17
Load roles & permissions — Role entities fetched by IDs from role table. Permissions fetched from permission table via findAllByRolesIdIn(). Role names and permission keys extracted.
18
JWT built via JwtService.generateToken() — claims injected: userId, credentialsId, companyId, employeeId, roles, authorities. Signed with HS256, 64-byte key derived from jwt.secret config.
19
First-login check — loads latest TemporaryCredentials for this email. If the temp password (BCrypt) still matches current credentials → isFirstLogin=true. Frontend will redirect user to change-password screen.
20
LoginResponse returned — { token, email, roles, permissions, isFirstLogin }. Frontend stores JWT in localStorage["session_token"]. Axios interceptor auto-attaches it to all future requests.
21
Frontend calls GET /current-user — with the JWT in Authorization header. Gateway validates token, injects userId, companyId, employeeId, credentialsId, username as request attributes. Auth Service reads them without parsing JWT itself.
22
Full profile assembled — Auth Service builds UserInfoDto: fetches company list from Company Service, resolves company logos from File Service. Frontend renders dashboard with correct menus based on permissions.
JWT Token Structure
// Header (encoded)
{ "alg": "HS256", "typ": "JWT" }

// Payload claims
{
  "sub": "user@example.com",              // credentials.email (getUsername())
  "userId": "uuid-...",                 // users.id
  "credentialsId": "uuid-...",          // credentials.id
  "companyId": "uuid-...",             // active company (baked in at login or change-company)
  "employeeId": "uuid-...",            // employee record at that company
  "roles": ["Administrator"],           // role names (human-friendly)
  "authorities": ["VIEW_EMPLOYEES", "CREATE_PAYROLL"], // permission keys
  "iat": 1718000000,                 // issued at (epoch ms)
  "exp": 1718086400                  // expiry — set by jwt.expiration config
}

// Signature: HMAC-SHA256 with 64-byte key derived from jwt.secret (bytes, copied to 64 bytes)
HMACSHA256(base64(header) + "." + base64(payload), Keys.hmacShaKeyFor(secret.getBytes()))
Gateway uses this token
The API Gateway's AuthenticationPrefilter validates the JWT on every request, then injects its claims as headers: userId, companyId, employeeId, credentialsId, username, token. Backend services read these headers — they never parse JWT themselves.
